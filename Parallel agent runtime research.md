# Parallel coding agents still duplicate their runtimes

Nobody has built or announced a local daemon, in Rust or any other language, that lets N coding agents in N git worktrees share copy-on-write dependencies, a parse/transform cache, one TypeScript checker with per-worktree overlays, and a port broker. That verdict rests on a survey, as of November 1, 2026, of eleven orchestrators, five agent vendors, and the worktree, language-server and dev-proxy tools around them. Three of the four layers already have shipping pieces: Worktrunk (Rust, 8.3k GitHub stars) and at least four smaller tools reflink `node_modules` and build output into new worktrees ([worktrunk.dev](https://worktrunk.dev/step/)), pnpm's docs recommend its global virtual store for one-worktree-per-agent setups ([pnpm](https://pnpm.io/git-worktrees)), Turborepo 2.8 shares its local cache across worktrees automatically ([Turborepo 2.8, Jan 23, 2026](https://turborepo.dev/blog/2-8)), and Vercel Labs' Portless routes `<branch>.localhost` to each worktree's dev server ([Portless](https://github.com/vercel-labs/portless)). The missing layer, the shared type checker, carries the largest RAM payoff: Claude Code's TypeScript plugin starts a **2–4 GB tsserver for every session, "not shared between sessions, even for the identical project root"** ([claude-code#87301, Aug 16, 2026](https://github.com/anthropics/claude-code/issues/87301)), and four agents filled the swap of a 16 GB host in a report filed October 31, 2026 ([PostHog/coherence#170](https://github.com/PostHog/coherence/issues/170)). That layer became buildable on October 20, 2026, when **TypeScript 7.1 Beta shipped an API with independent immutable snapshots, per-snapshot filesystem layers, and one shared content-hashed parse cache** ([TS 7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)). Two limits bound the payoff: the cache key includes the file path, so a daemon must present each worktree's edits at the base checkout's paths and translate paths in every result, and checker state stays per program, so only parsing and binding are deduplicated. The opportunity is an agent-agnostic daemon whose novel core is a tsgo snapshot broker; copy-on-write (CoW) seeding, port routing and process supervision are integration work on mature crates rather than inventions.

## Eleven orchestrators stop at setup, and vendors stop at symlinks

The orchestration layer is crowded, funded and uniformly shallow. **Conductor raised a $22M Series A on March 30, 2026** and reported 10x user growth since January ([Conductor blog](https://www.conductor.build/blog/series-a)), yet its documented setup script runs `pnpm install`, copies `.env` and runs `pnpm run build` in every workspace, it hands each workspace ten ports starting at `CONDUCTOR_PORT`, and its stop action "does not walk the descendant process tree, so processes that leave the group can keep ports open" ([Conductor scripts docs](https://www.conductor.build/docs/reference/scripts)). The open-source field follows the same template, with star counts read from GitHub on November 1, 2026. Vibe Kanban (Rust backend, **28.1k stars**) gives each agent "a branch, a terminal, and a dev server" and announced its sunset on April 10, 2026 ([GitHub](https://github.com/BloopAI/vibe-kanban); [shutdown post](https://vibekanban.com/blog/shutdown)). Superset (14.9k) concedes that worktrees "do not sandbox processes" ([GitHub](https://github.com/superset-sh/superset)). Claude Squad (8.3k), Emdash (6.0k), Container Use (4.1k), Crystal (3.1k, deprecated in February 2026 for Nimbalyst), Jean (1.3k, Tauri and Rust), uzi, Imbue's Sculptor and CodeRabbit's gtr (1.8k) all create a worktree or container, run setup, and stop ([Claude Squad](https://github.com/smtg-ai/claude-squad); [Emdash](https://github.com/generalaction/emdash); [Container Use](https://github.com/dagger/container-use); [Crystal](https://github.com/stravu/crystal); [Jean](https://github.com/coollabsio/jean); [uzi docs](https://www.mintlify.com/devflowinc/uzi/concepts/architecture); [Imbue docs](https://docs.imbue.com/features/containers); [gtr](https://github.com/coderabbitai/git-worktree-runner)). **None of the eleven documents sharing `node_modules`, caches or language servers across worktrees.**

The agent vendors share configuration between worktrees, not runtime. Claude Code's docs tell users to "ask Claude to install dependencies" in each fresh checkout and list only config (the `.git` directory, plugins, permission approvals) as shared ([Claude Code worktrees docs](https://code.claude.com/docs/en/worktrees.md)). Its one runtime concession is an opt-in `worktree.symlinkDirectories` setting ([settings reference](https://code.claude.com/docs/en/settings-reference)), which a third-party source mirror shows defaulting to an empty list ([tangled.org mirror](https://tangled.org/oppi.li/claude-code/raw/main/utils/worktree.ts)) and which has drawn bug reports for silent cleanup failures and for writes that replace the symlink with a regular file ([#40259](https://claudeissues.com/issue/40259-symlinkdirectories-causes-silent-worktree-cleanup-failure); [#40857](https://claudeissues.com/issue/40857-bug-symlinkdirectories-writing-to-symlinked-file-replaces-symlink-with-regular-f)). Codex states that each worktree "has its own set of repository files, dependencies, build caches" ([Codex docs](https://learn.chatgpt.com/docs/environments/git-worktrees)). Cursor goes further, warning "We do not recommend symlinking dependencies into the worktree" and capping machines at 25 worktrees from version 3.5 ([Cursor docs](https://cursor.com/docs/configuration/worktrees)). Neither VS Code's background-agent docs nor the Hacker News thread on Zed's parallel-agents launch mentions dependency or language-server sharing ([VS Code docs](https://code.visualstudio.com/docs/copilot/agents/background-agents); [HN 47866750](https://news.ycombinator.com/item?id=47866750)). The only user requests found are issue titles on Claude Code's tracker, #60113 asking to "reuse heavy dependency directories" and #63087 reporting worktrees "silently consuming disk space", whose status could not be read ([#60113](https://claudeissues.com/issue/60113-feature-agent-view-opt-out-of-worktree-isolation-and-reuse-heavy-dependency-dire); [#63087](https://claudeissues.com/issue/63087-agent-worktrees-are-never-cleaned-up-silently-consuming-disk-space)). **No vendor has announced shared language servers or runtime deduplication; vendor effort is going into disk.**

Language servers are shared today only when the paths match exactly. lspmux (formerly ra-multiplex, renamed in its 0.3.0 release on October 12, 2025) attaches a client to an existing server only when workspace and environment both match, and it drops server-initiated requests ([lspmux](https://codeberg.org/p2502/lspmux)). codescout 0.15.0 notes that each unshared session runs an LSP of "~2GB", but its mux covers only Rust and Kotlin, with "one kotlin-lsp per workspace path" ([codescout README](https://docs.rs/crate/codescout/latest/source/README.md); [servers/mod.rs](https://docs.rs/crate/codescout/latest/source/src/lsp/servers/mod.rs)). typemux-cc pools Python servers per `.venv` ([typemux-cc](https://github.com/k-dash/typemux-cc)), Serena runs one instance per project ([Serena discussion #1512](https://github.com/oraios/serena/discussions/1512)), catenary-mcp 1.4.0 runs one LSP per language with every root passed as a workspace folder ([catenary architecture](https://docs.rs/crate/catenary-mcp/1.4.0/source/docs/src/architecture.md)), and lspmux-rust-cc shares rust-analyzer among editors and agents "working in the same Rust workspace" ([claudepluginhub](https://www.claudepluginhub.com/plugins/billf-lspmux-rust-cc)). Because each worktree has its own path, every one of these tools starts or pools a separate server per worktree, and **no multiplexer was found that maps different worktree roots onto one server with diff overlays.** The one team found to escape the duplication did so by abandoning worktrees: Trigger.dev measured "9.82 GB across two worktrees" on a roughly 2 GB codebase, plus duplicated Postgres, Redis and ClickHouse, and moved to GitButler's single working directory, accepting the maintainers' warning that "overlapping areas can definitely lead to problems related to races and interference" ([Trigger.dev blog, Apr 16, 2026](https://trigger.dev/blog/parallel-agents-gitbutler)).

| Layer | Most advanced tool shipping today | Shared while agents run? | What is still missing |
|---|---|---|---|
| CoW dependencies | Worktrunk `wt step copy-ignored` (Rust, 8.3k stars); parhel, cow, Switchboard, agentbrew; pnpm global virtual store | No. Seeded once at creation, then independent (pnpm's store is the exception: one shared, writable store) | Lockfile-matched donor selection, absolute-path fix-ups, an ext4 fallback; not novel |
| Parse/transform cache | Turborepo 2.8 cross-worktree `.turbo/cache`; sccache `basedirs` | Task outputs only | A content-hash transform cache for test runners; modest value |
| Shared TS checker | None; muxes share only identical paths | No | **The core gap.** Feasible on the TS 7.1 API |
| Port/dev-server broker | Portless `.localhost` proxy; portree; Conductor's 10-port ranges | Routing yes; process ownership no | Daemon-owned dev servers with per-agent memory budgets |

## Two to four gigabytes per agent, times N, outruns 2026 laptops

The cost of parallel agents lives in the toolchain each agent spawns, not in the agent. A healthy Claude Code process uses **178–297 MB** ([claude-code#18859, Jan 2026](https://github.com/anthropics/claude-code/issues/18859)), while the language server, dev server and type-check runs it triggers each take gigabytes, and every worktree runs its own copy. The table collects the measured figures, dated by report or publication.

| Component | Measured figure | Source and date |
|---|---|---|
| tsserver per Claude Code session | 2–4 GB steady state; live readings 4,181 / 3,109 / 2,576 / 469 MB; two sessions on one repo ≈ 6.6 GB; a runaway instance reached 61.5 GB commit charge after 6h20m | [claude-code#87301](https://github.com/anthropics/claude-code/issues/87301), Aug 16, 2026 |
| Per-worktree warm server (Coherence) | serve 71 MB + LSP 58 MB + tsserver 485 MB ≈ 614 MB at rest; tsserver 0.7–1.4 GB in use; 4 sessions ≈ 3.2 GB, swap full, load average 46 on 8 cores | [PostHog/coherence#170](https://github.com/PostHog/coherence/issues/170), Oct 31, 2026 |
| Next.js dev server after 50 routes | vercel.com dashboard 21.5 GB → 2 GB; nextjs.org 4,600 MB → 840 MB after 16.3 memory eviction | [Next.js blog](https://nextjs.org/blog/next-16-3-turbopack), Jun 29, 2026 |
| Turbopack dev server, large app | ~7 GB versus ~3 GB on webpack (Next.js 16.2.3) | [next.js discussion #93451](https://github.com/vercel/next.js/discussions/93451), May 4, 2026 |
| Full type-check build | VS Code repo 5.2 GB (TS 6) → 4.2 GB (TS 7) | [TS 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), Jul 8, 2026 |

Adding a healthy agent (~0.3 GB), one tsserver (2–4 GB) and one Next.js dev server in the nextjs.org range (0.8–4.6 GB) gives **roughly 3–9 GB per active agent before test runs or leaks, and 15–45 GB for five agents; both figures are my estimates** built from the measurements above. Once the OS and editor are counted, nearly all of that five-agent range overruns the base 14-inch M5 MacBook Pro, announced October 15, 2025 with 16 GB ([MacRumors](https://www.macrumors.com/2025/10/15/apple-announces-macbook-pro-with-m5-chip/)), and the base M5 Pro, announced March 3, 2026 with 24 GB as the 14-inch model's price rose $200 to $2,199 ([Engadget](https://www.engadget.com/computing/laptops/apple-brings-its-m5-pro-and-max-silicon-to-the-next-macbook-pro-generation-141553279.html)). Upgrading is costlier than usual, with consumer RAM prices up "hundreds of percent" and Micron not expecting supply relief until 2028 ([Tom's Guide, Feb 23, 2026](https://www.tomsguide.com/computing/ram-price-crisis-2026-everything-you-need-to-know)). One shared checker per repository would save at most (N−1) × 2–4 GB, or **8–16 GB at five agents (an estimate and an upper bound)**, which is exactly the fix the #87301 reporter requested: "sharing one language server per project root across sessions" ([#87301](https://github.com/anthropics/claude-code/issues/87301)). How much of that bound is real depends on how tsgo's memory splits between shareable syntax trees and per-program checker state, discussed in the checker section.

Vendors are shrinking individual tools, which is a genuine headwind. Next.js 16.3's eviction cut its own dev server's memory by roughly 82–91% on Vercel's chart (my arithmetic from the two data points) ([Next.js blog](https://nextjs.org/blog/next-16-3-turbopack)), TypeScript 7 cut build memory 18% on the VS Code repo ([TS 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)), and pnpm's global store makes extra worktrees "nearly free in disk space" ([pnpm](https://pnpm.io/git-worktrees)). Many of the most dramatic figures are also leaks, such as four idle Claude Code sessions at about 15 GB each ([#18859](https://github.com/anthropics/claude-code/issues/18859)), 108 GB of memory with 41.6 GB of swap on a 36 GB M5 Max ([#56960](https://github.com/anthropics/claude-code/issues/56960)), and a Codex restart that freed about 24 GB ([codex#35269](https://github.com/openai/codex/issues/35269)). Critics will answer "fix the leak". **The defensible claim is the steady-state duplication of 2–4 GB of tsserver and roughly 1–5 GB of dev server per worktree, which no single vendor removes because each sees only its own process.** Disk evidence is weaker and comes mostly from tool authors: the author of the Rust tool workz claims about 2 GB per `node_modules`, five worktrees shrinking from about 12 GB to 3.5 GB by symlinking, and 3–5 minutes of `npm install` per setup, in a post dated March 4, probably 2026 ([rohansx, dev.to](https://dev.to/rohansx/every-ai-agent-tool-creates-git-worktrees-none-of-them-make-worktrees-actually-work-3ae9)); Switchboard measured about 700 MB per worktree across six ([PR #107, Sep 23, 2026](https://github.com/tejasnafde/switchboard/pull/107)); and agentbrew counted "about 6m52s per day" lost to dependency setup ([PR #371, Oct 22, 2026](https://github.com/fyodoriv/agentbrew/pull/371)).

Demand is broad, but no survey measures how many agents developers run at once. JetBrains' survey of 15,000+ developers (fieldwork May–July 2026) found **90% use AI coding agents at work at least weekly and 68% daily**, with Claude Code at 39% (up from 18% in January 2026) and Codex at 16% (up from 3%) ([JetBrains Research, Aug 2026](https://blog.jetbrains.com/research/2026/08/ai-coding-agent-adoption-2026/)). Stack Overflow's 2026 survey, published October 6, found 66% of AI users work in coding agents ([Stack Overflow blog](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/)); neither asks about parallel use. A small, self-selected Product Hunt poll from around early 2026, with its vote count hidden, found 81% run two or more Claude Code instances and 50% run three or more ([Product Hunt](https://www.producthunt.com/p/claude/how-many-claude-codes-do-you-run-in-parallel?page=2)), Claude Code's creator reportedly runs about ten sessions at once ([dev.to](https://dev.to/lassiecoder/how-claude-codes-creator-ships-50-100-prs-per-week-4oeo)), and Codex reported 4M weekly developers on April 21, 2026 ([OfficeChai, Jun 1, 2026](https://officechai.com/ai/openais-codex-reaches-5-million-users-resets-rate-limits-for-users/)). Every major vendor now ships worktree-parallel agents: Claude Code added `--worktree` on February 21 (2026, inferred from version 2.1.50) ([ThreadReader](https://threadreaderapp.com/scrolly/2025007393290272904)), and headlines report Cursor 2.0 running up to eight parallel agents in October 2025 and OpenAI's Codex macOS app in February 2026, though those articles were not opened ([Techzine](https://www.techzine.eu/news/devops/135916/cursor-2-0-introduces-parallel-agents-and-new-model/); [TechInformed](https://techinformed.com/openai-ships-codex-macos-app-as-ai-coding-shifts-toward-parallel-agents/)). Hacker News lists 267 "worktrees agents" stories since January 2025, yet Show HN launches drew 1–13 points, and Riftri's CoW-worktree launch on September 22, 2026 earned 5 points and one reply: "Let's see how it handles node_modules" ([HN Algolia](https://hn.algolia.com/api/v1/search?query=worktrees%20agents&tags=story&numericFilters=created_at_i%3E1735689600&hitsPerPage=20); [Riftri](https://news.ycombinator.com/item?id=49807251)). **I estimate the reachable audience at low hundreds of thousands to a few million developers running several local agents in worktrees; this band is my estimate, not a sourced figure.**

The exit pattern for fast open-source developer tooling has been acquisition by a platform or AI lab. OpenAI bought Astral on March 19, 2026, citing "an installed base of several million developers" ([SiliconANGLE](https://siliconangle.com/2026/03/19/openai-acquires-open-source-python-tooling-startup-astral/)), a deal Simon Willison compared with Anthropic's December 2025 purchase of Bun ([Business Today, Mar 20, 2026](https://www.businesstoday.in/technology/story/openais-astral-deal-reveals-hidden-funding-rounds-investor-windfall-simon-willison-521585-2026-03-20)). VoidZero joined Cloudflare on June 4, 2026 with monetization "still unsolved" ([voidzero.dev](https://voidzero.dev/posts/voidzero-cloudflare)), and Vercel acquired Turborepo in December 2021 and monetized remote caching ([turborepo.dev](https://turborepo.dev/blog/joining-vercel)).

## Layer by layer: what exists, how to build it, where it breaks

### Copy-on-write dependencies are a commodity with sharp edges

Copy-on-write seeding is the most crowded layer. Worktrunk's `wt step copy-ignored` copies every gitignored file, `node_modules/` and `target/` included, reflinking "where the filesystem supports it: APFS (macOS), btrfs and XFS (Linux), ReFS (Windows)" and falling back to full copies on ext4 and NTFS; its docs report a **14 GB `target/` taking about 2 minutes with `cp -R` versus about 20 seconds by reflink**, and a first Rust build dropping from about 68 s to about 3 s ([worktrunk.dev/step](https://worktrunk.dev/step/); [GitHub](https://github.com/max-sixty/worktrunk)). Smaller entrants report similar author-measured gains. parhel (5 stars) creates a worktree in 0.5 s and about 8 MiB versus 6.9 s and 383 MiB for `git worktree add` plus `cp -R` ([parhel](https://github.com/myrk-kale/parhel)). cow (19 stars) clones "2 GB repo[s] in ~130 ms" and exposes MCP tools through its cow-cli 0.1.4 crate ([cow](https://github.com/joeinnes/cow); [cow-cli README](https://docs.rs/crate/cow-cli/0.1.4/source/README.md)). Switchboard's PR #107 (merged September 23, 2026) clones a 934 MB `node_modules` in about 6.3 s with no added disk ([PR #107](https://github.com/tejasnafde/switchboard/pull/107)), and agentbrew's PR #371 (merged October 22, 2026) cut a fresh worktree's dependency step from 11.7–13.3 s to about 1.2 s ([PR #371](https://github.com/fyodoriv/agentbrew/pull/371)). Grove, a Go tool built around a warm "golden copy", was archived on September 22, 2026 ([Grove](https://github.com/chrisbanes/grove)). Package managers attack the same cost from the other side. pnpm's global virtual store (`virtualStoreType: global`, experimental and off by default for project installs) leaves each worktree's `node_modules` as symlinks into one shared store, so later installs are "nearly instant" ([pnpm GVS](https://pnpm.io/global-virtual-store); [pnpm git worktrees](https://pnpm.io/git-worktrees)); Bun clones from its cache on macOS and hardlinks on Linux and Windows ([Bun install docs](https://bun.com/docs/pm/cli/install)); and Yarn Berry's PnP linker and Deno's `nodeModulesDir: none` skip a per-project `node_modules` entirely ([Yarn](https://yarnpkg.com/configuration/yarnrc); [Deno](https://docs.deno.com/runtime/fundamentals/node/)).

The operating-system primitives are well documented and differ sharply by platform. On macOS, `clonefile(2)` (OS X 10.12+) clones a whole directory hierarchy in one atomic call, although the man page "strongly discourage[s]" that use; it fails with `EXDEV` across volumes and `ENOTSUP` on unsupported ones, clears setuid bits, and can return `ENOSPC` on a later write to a shared block ([clonefile(2)](https://keith.github.io/xcode-man-pages/clonefile.2.html)). `copyfile(3)` with `COPYFILE_CLONE | COPYFILE_RECURSIVE` is the sanctioned alternative and lets a callback return `COPYFILE_SKIP` to prune subtrees such as `.git`, but it is not atomic and does not preserve hard links ([copyfile(3)](https://keith.github.io/xcode-man-pages/copyfile.3.html)). On Linux, `ioctl(FICLONE)` and `FICLONERANGE` (Linux 4.5) reflink single files on btrfs and XFS and offer no directory clone ([ioctl_ficlone(2)](https://man7.org/linux/man-pages/man2/ioctl_ficlone.2.html)), so a daemon must walk the tree itself and recreate directories and symlinks. The maintained crate is **`reflink-copy` 0.1.31 (released November 1, 2026; 5.27M downloads in 90 days)**, which calls `clonefile` on macOS and rustix's `ioctl_ficlone` on Linux; its `reflink_or_copy` has no directory fallback, and `check_reflink_support` returns `Unknown` outside Windows ([crates.io](https://crates.io/crates/reflink-copy); [lib.rs](https://github.com/cargo-bins/reflink-copy/blob/main/src/lib.rs)). The only real-world timing for a large `node_modules` comes from pnpm discussion #14041 (August 20, 2026): on an M4 Pro, a workspace of about 212,896 files in about 41,000 directories took 44 s to install fresh and **13.4 s to seed with a single `clonefile`**, "almost entirely directory clone", or roughly 60 µs per entry by my arithmetic, while seeding from a stale donor took 78 s, worse than not seeding at all ([pnpm #14041](https://github.com/orgs/pnpm/discussions/14041)). APFS cloning is metadata-bound rather than instant, so a daemon should pre-warm a pool of worktrees off the critical path.

The same discussion catalogues edge cases a daemon must automate. `node_modules/.pnpm-workspace-state-v1.json` stores absolute paths that must be rewritten, `lastValidatedTimestamp` must be reset because checkout mtimes otherwise trigger reinstalls, and a donor is valid only when lockfile and manifests are byte-identical ([pnpm #14041](https://github.com/orgs/pnpm/discussions/14041)). Shims with absolute paths break on relocation ([pnpm #7341](https://github.com/orgs/pnpm/discussions/7341)), whereas aube's `$basedir`-relative shims survive it ([aube PR #613](https://github.com/endevco/aube/pull/613)). The mutation model matters more than speed. pnpm warns that under hardlinking a `node_modules` file *is* the store file, so "If you edit files inside `node_modules`, ask for `clone` explicitly" ([pnpm settings](https://pnpm.io/settings/node-modules)), and it tells users to share a global store only among "projects, users, and jobs that trust each other" ([pnpm GVS](https://pnpm.io/global-virtual-store)). It follows that cloning a `node_modules` built from symlinks into a global store copies the links, not the data, leaving the clone coupled to every other worktree. Clones also mislead disk accounting: in one test Finder's "size on disk" never moved while a clone's real usage grew from 0.74 GB to 65.05 GB ([Eclectic Light, Sep 5, 2026](https://eclecticlight.co/2026/09/05/when-the-finders-size-on-disk-is-misleading/)). On Linux, each cloned worktree adds watcher load, and Cursor's extension host and file watcher alone consumed 65,532 of 65,536 inotify watches on Ubuntu 22.04, breaking Vite with `ENOSPC` ([Cursor forum, Jun 7, 2026](https://forum.cursor.com/t/linux-extensionhost-filewatcher-exhaust-inotify-limit-65k-blocks-vite-dev-tools-enospc/162635)), with each watch costing about 1 kB of unswappable kernel memory under a per-user limit ([Coder docs](https://coder.com/docs/guides/troubleshooting/inotify-watch-limits)). Most important for the pitch, **no source confirmed that reflinked files share page cache**, so N dev servers reading N cloned `node_modules` trees may still load N copies into RAM; until measured, CoW should be sold on disk and setup time, not memory.

Filesystem support caps the audience. APFS clones on every modern Mac, XFS has enabled reflink by default since xfsprogs 5.1 ([Oracle](https://blogs.oracle.com/linux/post/xfs-data-block-sharing-reflink)), OpenZFS block cloning shipped in 2.2.0 with a data-corruption bug and was disabled by default in 2.2.1 on November 22, 2023 before current master docs listed it as on by default ([zfs-2.2.1](https://github.com/openzfs/zfs/releases/tag/zfs-2.2.1); [zfs(4)](https://openzfs.github.io/openzfs-docs/man/master/4/zfs.4.html)), and Windows 11 24H2 added block cloning on Dev Drive ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/dev-drive/)). ext4 and NTFS, the defaults on Ubuntu, WSL2 and Windows, cannot reflink. Stack Overflow's 2025 survey puts professional use at Windows 49.5%, macOS 32.9%, Ubuntu 27.7% and WSL 16.8% ([SO 2025](https://survey.stackoverflow.co/2025/technology)), from which **I estimate only 35–45% of developers can reflink out of the box (an estimate; the survey does not ask about filesystems).** The fallback ladder runs from reflink to hardlinks from a store for immutable package files, then pnpm-style symlinks, then plain copies, and the daemon should tell users which tier they received. Linux adds one more rung: since kernel 5.11, overlayfs mounts without root inside a user namespace with `userxattr` ([LKML 5.11 pull request](https://lore.kernel.org/lkml/20201217142025.GB1236412@miu.piliscsaba.redhat.com/)), but only processes inside that namespace see the merged view, any write copies up the whole file, and directory renames fail with `EXDEV` unless `redirect_dir` is enabled ([kernel overlayfs docs](https://docs.kernel.org/filesystems/overlayfs.html)). macOS has no rootless overlay: macFUSE 5.5.0 (October 17, 2026) offers an FSKit backend whose I/O "is not on par" with its kernel extension ([macFUSE](https://macfuse.github.io); [FUSE backends wiki](https://github.com/macfuse/macfuse/wiki/FUSE-Backends)), fuse-t mounts through a loopback NFSv4 server ([fuse-t](https://github.com/macos-fuse-t/fuse-t)), and Turso's AgentFS layers a SQLite delta over a read-only base ([AgentFS](https://docs.turso.tech/agentfs/guides/overlay)). The gap in this layer is quality, not existence. At least eight implementations already seed or share dependencies per worktree, every seeding tool leaves each worktree running independent processes afterwards, and none documents lockfile-hash donor selection, automatic absolute-path and timestamp fix-ups, a good ext4 story, or a measured RAM benefit.

### Build caches split into shareable stores and clone-only state

The parse/transform cache in the brief overlaps with caches build tools already own, and those caches fall into two classes. Content-addressed stores with path-independent keys can be shared live. **Turborepo 2.8 (January 23, 2026) made linked worktrees "automatically share the main worktree's `.turbo/cache`"** unless `cacheDir` is set, although restored artifacts containing absolute paths are not rewritten ([Turborepo 2.8](https://turborepo.dev/blog/2-8); [caching docs](https://turborepo.dev/docs/crafting-your-repository/caching)), and sccache 0.15's `basedirs` strips checkout roots from cache keys to hit across "separate checkouts or Git worktrees" ([sccache configuration](https://docs.rs/crate/sccache/0.15.0/source/docs/Configuration.md)). Mutable working state cannot be shared live but can be cloned per worktree for a warm start. Next.js keeps Turbopack's persistent cache under `.next/`, on by default for dev since 16.1 and for build since 16.3, and says nothing about portability across directories ([Next.js docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/turbopackFileSystemCache)). Vite caches pre-bundled dependencies in `node_modules/.vite`, invalidated by lockfile content, patch-folder mtime and config ([Vite](https://vite.dev/guide/dep-pre-bundling)). A shared Nx cache errors across versions and lets parallel worktrees corrupt `nxdeps.json`, in an issue without a maintainer resolution ([nx#10000](https://github.com/nrwl/nx/issues/10000)). TypeScript's maintainers declined to support portable `.tsbuildinfo`, which validates by timestamp ([TypeScript#32023](https://github.1485827954.workers.dev/microsoft/TypeScript/issues/32023)), Jest names its cache `/tmp/<path>` ([Jest](https://jestjs.io/docs/configuration)), and Bazel names each output base after the MD5 of the workspace path, so every worktree starts a cold server ([Bazel](https://bazel.build/remote/output-directories)). Timestamp validators are the trap, since a clone that preserves mtimes can make stale state look fresh.

A daemon-owned parse cache adds little because parsing is cheap. oxc parses a large real-world TSX file (cal.com.tsx) in **4.0 ms against swc's 14.9 ms** on an M2 Mac mini ([oxc parser benchmark](https://github.com/oxc-project/bench-javascript-parser-written-in-rust)) and transforms it in 11.3 ms against 38.1 ms ([oxc transformer benchmark](https://github.com/oxc-project/bench-javascript-transformer-written-in-rust)); neither page is dated. I estimate typical files at 0.1–1 ms each, so re-parsing 10,000 files costs seconds per worktree against tens of seconds to minutes for type checking. A transform cache for test runners is easier to justify, since transforming costs nearly three times as much as parsing in oxc's numbers, but its key must include transformer version, options and path-dependent output such as sourcemaps. Rust-built ASTs cannot feed TypeScript's Go checker, so this cache cannot double as the checker's. gopls supplies the design to copy, a machine-global cache keyed by a SHA-256 "digest of the value's recipe" and readable across processes ([gopls filecache](https://pkg.go.dev/golang.org/x/tools/gopls/internal/filecache)), which helped gopls v0.12 cut memory about 75% on average across 28 repositories ([Go blog, Sep 8, 2023](https://go.dev/blog/gopls-scalability)). **This layer is unbuilt for agents but low in value**, and the evidence is thin because Vite, Vitest and Jest internal caching were not studied in depth.

### TypeScript 7.1's snapshot API makes the shared checker buildable

Classic tsserver (TypeScript 6.x and earlier) cannot serve one base plus many diffs without a fork. It keeps exactly one `ScriptInfo` text per path, either the open editor buffer or the disk contents ([scriptInfo.ts](https://github.com/microsoft/TypeScript/blob/050880ce59e30b356b686bd3144efe24f875ebc8/src/server/scriptInfo.ts)), and its `DocumentRegistry`, which lets language services share `SourceFile`s, keys entries by compiler-settings bucket and path and updates a shared entry in place when the version changes ([documentRegistry.ts](https://github.com/microsoft/TypeScript/blob/050880ce59e30b356b686bd3144efe24f875ebc8/src/services/documentRegistry.ts)). Two worktrees mapped onto one set of paths therefore cannot hold different contents for the same file, and an LSP `didOpen` overlay cannot express a deleted file. Inside Electron, tsserver also hits a 4 GB heap ceiling caused by V8 pointer compression ([vscode#127105](https://github.com/microsoft/vscode/issues/127105)).

TypeScript 7 changed the picture. TS 6.0 (March 23, 2026) was the last JavaScript-based release; **7.0, the native Go port, went final on July 8, 2026, and 7.1 Beta followed on October 20** ([TS devblog](https://devblogs.microsoft.com/typescript/)), with an RC promised "in about a month" ([7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)). The typescript-go staging repository is closed and the Go sources now live in microsoft/TypeScript `main` ([typescript-go README](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/README.md)). Microsoft reports full builds 8–12x faster (VS Code 125.7 s to 10.6 s), language-server crashes down more than 60%, and time to first error in the VS Code repo down from about 17.5 s to under 1.3 s, but **aggregate build memory down only 18% (5.2 GB to 4.2 GB on VS Code)** ([TS 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). Speed improved far more than memory, so N-way duplication still bites. TS 7.0 shipped no programmatic API, so typescript-eslint and the Vue, Svelte, Astro and Angular tooling cannot use it yet ([InfoQ, Aug 3, 2026](https://infoq.com/news/2026/08/typescript-7-released/)), and many repositories will run TS 6 tsserver alongside tsgo for months.

Internally, tsgo's language server is already shaped like a shared checker. A `Session` turns changes into immutable snapshots, and a reference-counted `ParseCache` holds the source files those snapshots share, releasing them when no snapshot references their program ([session.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/project/session.go#L104); [internal/project docs](https://pkg.go.dev/github.com/microsoft/typescript-go/internal/project)). The cache key is the decisive detail: **`ParseCacheKey` combines `FileName`, `Path`, an xxh3-128 content hash, the script kind and a few module-detection options**, but not the general compiler options ([parsecache.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/project/parsecache.go#L15); [parseoptions.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/ast/parseoptions.go#L8)), so identical content at a different path is not shared. Binding runs per source file, so bind results ride along with the shared tree, but checkers do not: each program owns a pool of four checkers by default, idle-cleaned after 30 s ([checkerpool.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/project/checkerpool.go#L17)). The LSP front end is the wrong entry point, because it holds one session-wide overlay map, derives a single working directory, uses a workspace folder only when there is exactly one, and has no `workspace/didChangeWorkspaceFolders` handler ([server.go](https://github.com/microsoft/TypeScript/blob/6161772c1370bdd4a82f808e6823bd755eb1870d/tsc/internal/lsp/server.go#L1748)); driving tsgo through LSP repeats tsserver's one-content-per-path limit.

The 7.1 API exposes the snapshot machinery directly. It ships `typescript/sync`, `typescript/async`, `typescript/fs` and `typescript/ast` entry points, in which a snapshot is "a version of all the projects and programs at a point in time", created with `api.createSnapshot` and derived with `snapshot.update(...)`; **`createFileSystemLayer(files)` "Overrides selected files while falling back to the base snapshot's file system, or the host file system"**, `removedPaths` "can block out requests from the underlying system", and changes arrive as `fileNotifications` rather than through built-in watching ([7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)). The source describes `CreateSnapshotParams` as parameters for "a new independent snapshot", and layers merge "base directory listings when omitted", so added files appear in tsconfig `include` globs ([fs.ts](https://github.com/microsoft/TypeScript/blob/6161772c1370bdd4a82f808e6823bd755eb1870d/packages/typescript/src/api/fs.ts#L145)). The server speaks MessagePack over stdio or a Unix-domain socket, and a `callbackFS` lets the client answer `readFile`, `fileExists` and directory-listing calls over RPC as a virtual filesystem ([api/server.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/api/server.go); [callbackfs.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/api/callbackfs.go)). Snapshots must be disposed, or "we'll leak on the Go side" ([7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)).

The design that follows is my proposal, and it is concrete. The daemon keeps one tsgo API process per repository and TypeScript version, holds a base snapshot of the main checkout, and gives each agent an independent snapshot whose layer contains that worktree's differences from base, re-rooted at base paths, with deletions listed in `removedPaths`. The layer must come from a content-hash diff of the filesystem rather than `git diff`, because untracked and generated files count. Every path in requests and responses is translated between `/base/...` and `/worktrees/<id>/...`, covering locations, related diagnostics, `WorkspaceEdit` keys and code-action edits. The table classifies which worktree changes this model absorbs, based on the API behavior cited above.

| Change in a worktree | One LSP server with `didOpen` overlays | tsgo 7.1 snapshot plus filesystem layer | Needs its own instance? |
|---|---|---|---|
| Edit to a tracked file | Works at base paths, but two agents editing one path collide | Works; each snapshot has its own layer | No |
| Added file | Partly; open files may miss tsconfig `include` globs | Works; layers merge directory listings | No |
| Deleted or renamed file | Fails; no way to mark a file absent | Works via `removedPaths` | No |
| tsconfig change | Reloads the project for every agent | Separate program in that snapshot; syntax trees still shared unless JSX or module-detection options change | Usually no |
| package.json `exports`/`type` change | Changes resolution for everyone | Resolved per snapshot (per-snapshot resolution caches unverified) | Usually no |
| Different lockfile or `node_modules` | Shares nothing | Shares only if `node_modules` resolves to the same real path | Yes, or a separate snapshot with its own `node_modules` |
| Different TypeScript version | Not applicable | Not applicable | Yes |
| Project references / `tsc -b` | Built outputs differ per worktree | Fine for editor queries; `.tsbuildinfo` stays per worktree | For `--build` runs |

The memory payoff is real but bounded, and nobody has measured it. TypeScript's own `DocumentRegistry` comment says `SourceFile` objects "account for most of the memory usage by the language service" ([documentRegistry.ts](https://github.com/microsoft/TypeScript/blob/050880ce59e30b356b686bd3144efe24f875ebc8/src/services/documentRegistry.ts)), and gopls found typed syntax trees "typically 30x larger than the source text" ([Go blog](https://go.dev/blog/gopls-scalability)), which suggests the shareable portion dominates at rest. Checker state, however, is the part that grows as agents ask questions, and it is rebuilt per snapshot, so N agents requesting full-program diagnostics still pay roughly N times the checker CPU and peak checker memory, released after the 30 s idle timeout. No published figure splits tsgo memory into syntax trees and checker state, and tsgo language-server memory on a large monorepo is unpublished too. **The (N−1) × 2–4 GB saving implied by #87301 is therefore an upper bound and an estimate**, and the first deliverable should be a benchmark of five 7.1 snapshots against five tsgo language-server processes on a real monorepo.

How agents reach the shared checker is the other hard edge. Over LSP, a per-agent shim must answer or route server-initiated requests such as `workspace/configuration`, `client/registerCapability` and `workspace/applyEdit`, which the specification assumes go to a single client ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)) and which lspmux simply drops ([lspmux](https://codeberg.org/p2502/lspmux)), and because diagnostics are keyed by URI the shim must attribute each one to its worktree. Over MCP, diagnostics, hover and references tools map cleanly onto per-snapshot API calls. Path filtering can break either route: typemux-cc reports that Claude Code filters results through `git check-ignore`, so `goToDefinition` and `findReferences` come back empty for paths inside "Claude Code's own worktrees" ([typemux-cc](https://github.com/k-dash/typemux-cc)). The beta announcement does not say whether the 7.1 API offers the full language-service surface, such as completions and rename, per snapshot, or how many independent snapshots can safely run at once.

**This is the genuine unbuilt gap.** The only prior art for base plus diffs is in code indexing, where Meta's Glean stacks an incremental database on an older one and hides the changed units, at about 7% extra database size and under 10% typical query overhead ([Glean, Dec 1, 2022](https://glean.software/blog/incremental/)). Among language servers, gopls and rust-analyzer use immutable snapshots with per-URI overlays designed for one editor on one workspace ([gopls design](https://github.com/golang/tools/blob/master/gopls/doc/design/implementation.md); [rust-analyzer architecture](https://rust-analyzer.github.io/book/contributing/architecture.html)), and only tsgo 7.1 offers independent snapshots with filesystem layers. The building block is Microsoft's own API, not an LSP multiplexer, and that API is still in beta.

### Port routing is solved in pattern; process ownership is not

The broker layer has a clear reference implementation. **Portless** (Vercel Labs, pre-1.0, Apache-2.0) assigns a random port in 4000–4999 through `PORT`, injects `--port` and `--host` for frameworks that ignore it such as Vite and Astro, prefixes the branch name as a subdomain inside linked worktrees, and runs one loopback-only proxy that forwards WebSockets over HTTP/1.1 `Upgrade` and HTTP/2 extended CONNECT so hot reload survives; it defaults to HTTPS with HTTP/2 from a local certificate authority because HTTP/1.1 caps browsers at six connections per host ([Portless](https://github.com/vercel-labs/portless)). A Vercel community post from February 26, 2026 wires it into Conductor's run script with every worktree sharing port 1355 ([Vercel Community](https://community.vercel.com/t/using-portless-with-conductor-git-worktrees/34557)). Alternatives include portree (Go, 25 stars), which hashes branch and service with FNV32 and routes by Host header ([portree](https://github.com/fairy-pitta/portree)), the Caddy-based worktree-devservers ([GitHub](https://github.com/viktormarinho/worktree-devservers)), and Coasts, whose only production-tested runtime is privileged Docker-in-Docker according to a secondary source ([Penligent, Mar 31, 2026](https://www.penligent.ai/hackinglabs/git-worktrees-need-runtime-isolation-for-parallel-ai-agent-development/)). Orchestrators also hand out ranges themselves, with Conductor giving ten ports per workspace, uzi assigning from a configured range, workz taking the next free port from 3000 and writing per-worktree database names into `.env.local`, and Worktrunk offering a `hash_port` template filter ([Conductor](https://www.conductor.build/docs/reference/scripts); [uzi](https://www.mintlify.com/devflowinc/uzi/concepts/architecture); [workz](https://dev.to/rohansx/i-got-tired-of-writing-the-same-80-line-setup-script-for-every-ai-worktree-4hj9); [Worktrunk](https://github.com/max-sixty/worktrunk)).

Browsers make `.localhost` routing nearly free. Chrome, Firefox and Edge resolve `*.localhost` to loopback without DNS setup while Safari relies on the system resolver ([Portless](https://github.com/vercel-labs/portless)), and WebKit reports `foo.bar.localhost` failing on macOS 15.7 but working on macOS 26 Tahoe, implemented "in OS frameworks below WebKit" ([WebKit bug 160504](https://bugs.webkit.org/show_bug.cgi?id=160504)), so only older Macs need `/etc/hosts` entries. Vite's `server.allowedHosts` accepts `.localhost` subdomains by default, and its hot-reload client errors when a proxy fails to forward WebSockets ([Vite server options](https://vite.dev/config/server-options)). Strict OAuth providers such as Google and Apple reject `.localhost` redirect URIs, and binding below port 1024 without root works on macOS only on the wildcard address, which Portless exploits while rejecting non-loopback peers, whereas Linux needs `net.ipv4.ip_unprivileged_port_start=80` ([Portless](https://github.com/vercel-labs/portless)); the daemon should default to an unprivileged high port. In Rust, `hyper` 1.12.0 (October 6, 2026) provides `hyper::upgrade` for splicing upgraded connections ([crates.io](https://crates.io/crates/hyper); [upgrade.rs](https://github.com/hyperium/hyper/blob/master/src/upgrade.rs)), and `rcgen` 0.14.10 generates the local certificate authority ([crates.io](https://crates.io/crates/rcgen)).

The hard edges are races and runaway processes. Any probe-then-assign scheme races the child's `bind`, worse when N agents start at once (my inference), so the daemon should own a port registry, probe both `127.0.0.1` and `::1`, and confirm the actual listener, which the `listeners` 0.6.1 crate maps to process IDs ([crates.io](https://crates.io/crates/listeners)). Process groups leak, as Conductor's stop action shows by signalling the group without walking descendants ([Conductor scripts docs](https://www.conductor.build/docs/reference/scripts)). On Linux, a delegated cgroup v2 provides an unescapable tree kill through `cgroup.kill` and memory accounting through `memory.current` and `memory.peak`, although memory stays charged to whichever cgroup touched it first, so shared page cache skews per-agent figures ([cgroup v2 docs](https://docs.kernel.org/admin-guide/cgroup-v2.html)); an unprivileged daemon gets its cgroup through systemd delegation ([systemd.io](https://systemd.io/CGROUP_DELEGATION/)). macOS has no cgroups, so per-agent memory must be summed from each descendant's `phys_footprint`, the figure Activity Monitor shows ([footprint(1)](https://keith.github.io/xcode-man-pages/footprint.1.html)), because the popular `sysinfo` crate reports resident set size instead ([sysinfo process.rs](https://github.com/GuillaumeGomez/sysinfo/blob/main/src/unix/apple/macos/process.rs)).

The gap here is process ownership, not routing. Portless deliberately omits dev-server launch tools from its MCP server because "MCP has no detached form" ([Portless](https://github.com/vercel-labs/portless)); a daemon that owns process lifecycles removes that limit, so an agent can call `start_dev_server` and get a URL back immediately. Current responses to memory pressure are blunt: coherence#170 proposes a machine-wide cap with least-recently-used eviction and idle timeouts ([coherence#170](https://github.com/PostHog/coherence/issues/170)), and one developer built `agent-flock`, a machine-wide lock that serializes heavy commands, after two type-checks in two worktrees pushed a laptop into swap ([koenvg, Aug 29, 2026](https://dev.to/koenvg/when-worktrees-share-ram-gba)). **A broker combining routing, per-agent memory budgets and one shared checker would be new; a broker that only routes would compete with free, Vercel-backed Portless.**

Three choices need explanation. For git, shell out rather than use a library: gitoxide's status page lists "move, remove, and repair linked worktrees" as not yet done, and `git2` 0.21.0 is tied to libgit2 1.9.7+ semantics ([gitoxide crate status](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md); [git2-rs](https://github.com/rust-lang/git2-rs)). `git worktree add --lock` creates and locks atomically, which also protects against pruning, and because worktrees share refs and the object store ([git-worktree docs](https://git-scm.com/docs/git-worktree)), repository-wide operations such as fetch, gc and branch creation should be serialized through the daemon. For the checker bridge, the daemon should not implement a type checker; it should spawn tsgo's API server and speak MessagePack over stdio or a Unix socket ([api/server.go](https://github.com/microsoft/typescript-go/blob/89d5d5b2849a0db0957065889ca58536fa6d2e4a/internal/api/server.go)). The official client is the JavaScript `typescript/async` package ([7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)), and because the protocol is in beta and no Rust client was found, my recommendation is a small Node sidecar using the official client until 7.1 is final, with a native Rust client later. For distribution, copy Biome's launcher with `optionalDependencies` on ten platform packages ([Biome package.json](https://github.com/biomejs/biome/blob/main/packages/@biomejs/biome/package.json)) and esbuild's embedded SHA-256 binary hashes with a registry-download fallback ([esbuild package.json](https://github.com/evanw/esbuild/blob/main/npm/esbuild/package.json); [node-install.ts](https://github.com/evanw/esbuild/blob/main/lib/npm/node-install.ts)). Ship a Homebrew formula rather than a cask, since casks failing Gatekeeper lose support on September 1, 2026 ([Homebrew#20755](https://github.com/Homebrew/brew/issues/20755)), and run the daemon as a per-user LaunchAgent or `systemctl --user` unit, which `service-manager` 0.11.0 abstracts ([service-manager](https://crates.io/crates/service-manager)). Signing macOS binaries from Linux CI with `apple-codesign` is possible, but that crate's last release was November 29, 2024 ([crates.io](https://crates.io/crates/apple-codesign)).

## Conclusion

The research moves the opportunity from disk to memory. Disk space and install time are close to solved by vendors, package managers and at least eight small tools; duplicated RAM is not, and it collides with 16–24 GB base laptops during a DRAM price spike. The one genuinely novel component, a shared tsgo checker with per-worktree layers, is buildable only because Microsoft's 7.1 API already deduplicates internally, which makes the technical moat thin. The daemon's lasting value lies in the agent-agnostic plumbing around that API, namely re-rooting each worktree's changes at base paths, choosing instances by lockfile, translating paths, and enforcing per-agent memory budgets, which no single agent vendor has a reason to build for competitors' agents, and which can plug into existing hooks such as Claude Code's `WorktreeCreate` and Conductor's setup scripts ([Claude Code worktrees docs](https://code.claude.com/docs/en/worktrees.md); [Conductor scripts docs](https://www.conductor.build/docs/reference/scripts)).

Two unknowns should be retired before anything is promised: what share of tsgo's resident memory sits in shareable syntax trees rather than per-snapshot checker state, and whether reflinked `node_modules` trees share page cache. A benchmark answering both on a real Next.js monorepo with five agents is the right first artifact, and it doubles as the launch post the demand evidence calls for, since Show HN orchestrators score in single digits while gigabyte-denominated charts from Vercel and bug reports quoting swap usage are what moved vendors this year.
